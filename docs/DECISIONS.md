## D9 · 2026-08-19 · Base model family: Qwen3.5 (0.8B/4B/9B) for all three rungs; GRPO via veRL, not TRL
Rationale: Verified against real `config.json` files per `PLAN.md` §11.2, not model cards or industry roundups (see `PLAN-DAY-01.md` Block 6). Qwen3.5 uses a 3:1 hybrid attention layout — 3 Gated DeltaNet (linear attention) layers per 1 Gated Attention (full attention) layer, confirmed via `layer_types` / `full_attention_interval: 4` in `Qwen/Qwen3.5-{0.8B,4B,9B}-Base`'s configs — versus plain Qwen3's uniform full attention. Three measured advantages: (1) native context is 262,144, well past the 65,536 target, so the YaRN phase (`PLAN.md` §5, days 25–32) is skipped entirely; (2) KV cache at 64K is ~4x smaller than Qwen3's equivalent rung, since only the 1-in-4 full-attention layers scale with context — Qwen3.5-4B needs ~1.1 GB Q8 KV @ 64K vs. Qwen3-4B's ~4.8 GB, and stays comfortable even at its full native 262K (~4.3 GB Q8), where plain Qwen3 would need ~19 GB and blow the 12 GB deployment target (`PLAN.md` §3.4); (3) recall/retrieval at this exact 3:1 ratio is not degraded — a systematic academic study (arXiv:2507.06457) found hybrid recall "approaches or exceeds" the full-attention baseline at 3:1, and production RULER numbers for the architectural predecessor (Qwen3-Next-80B-A3B) beat same- and larger-sized full-attention Qwen3 MoE models at every length ≤256K. One real blocker was found and routed around: TRL's `GRPOTrainer` with vLLM `colocate` mode fails on Qwen3.5 text-only checkpoints (weight-prefix mismatch — `QwenLM/Qwen3.6#64`, mirrored at `vllm-project/vllm#36275`; never fixed on that thread, only stale-bot closed). veRL has a merged, reviewed alternative (`verl-project/verl#5682`, merged 2026-03-30, GRPO+FSDP for Qwen3.5) with a since-merged hardening fix for a sequence-parallelism edge case (`#6660`) — and `PLAN.md` §9 already lists veRL as an equal alternative to TRL, so this is a routing choice, not a new dependency. Going all-Qwen3.5 rather than mixing with Qwen3 keeps one tokenizer across all three rungs, preserving the free speculative-decoding draft (§7.4) and an unconfounded Ablation A6. Rung sizes are 0.8B/4B/9B, not the literal 0.6B/8B named in `PLAN.md` §2 — the closest Qwen3.5 dense sizes exist at 0.8B and 9B, not 0.6B/8B; §2's own sizes are stated with "~", so this is within its intent. Licence: Apache 2.0, confirmed, no blocker.
Revisit if: the veRL Qwen3.5 GRPO path fails an actual smoke test on our cluster (not yet run — do before committing the day-33 GRPO phase); the `FLA` / `causal_conv1d` kernel install fails in our environment; AWQ/GPTQ/GGUF quantization tooling doesn't support the hybrid layers cleanly by day 54; or a newer point release (Qwen3.6/3.8 already exist as of Aug 2026) offers materially better tooling maturity before weights are committed for SFT.

## D10 · 2026-08-19 · W&B project, run-naming scheme, and required per-run fields
Rationale: `PLAN-DAY-01.md` Block 7. One project, `legalpsy`, under the personal entity `joshi0494` — not split per phase or per model size, because the ablations this project runs on (A3 long-context-vs-retrieval, A6 cross-rung scaling) are themselves cross-phase/cross-size comparisons that a split-project layout would make harder, not easier; revisit the entity (not the single-project structure) if a public release later wants a team entity instead of a personal one. Run name: `{phase}-{model}-{split}-{promptver}-{date}-{githash7}`, phases fixed to `eval|base|sft|yarn|grpo|abl|quant`. Four decisions on top of the plan's literal template, made now while zero real runs exist: (1) `model` is family+size (`qwen3.5-4b`, not `4b`) so a run is unambiguous if D9 ever gets revisited into a mixed-family project; (2) `date` is `YYMMDD` (`260819`), not the plan's literal `MMDD`, to avoid a year-boundary collision if this project is revisited past 2026; (3) `promptver` uses the `v1`/`v2` prefix to match the existing `configs/prompts/v1.yaml` convention (`PLAN-DAYS-1-7.md` Day 6), reconciling a mismatch against Block 7's own `p1` example; (4) the local `runs/<name>/` output directory (Day 6's `metrics.json` / `generations.jsonl` / `failures.csv` / `table.md`) uses this exact same string, so a run can always be mapped filesystem↔W&B without a separate lookup. Every run logs, per Block 7's list, a metrics table, a generations table (`PLAN.md` §9 — "log generations, not just scalars"), the resolved config, prompt hash, split manifest hash, git SHA, and model id; tags are `[phase, model_token, split, prompt_version]`. Enforced structurally, not by convention alone: `src/legalpsy/tracking.py`'s `RunMeta` (pydantic) makes all seven fields required — a run missing one fails to construct rather than silently omitting it — and `start_run()` builds the name/tags from `RunMeta` so no script hand-assembles the string. `git_sha` is computed automatically (`git rev-parse --short=7 HEAD`); `prompt_hash` / `split_manifest_hash` are meant to be `file_sha256()` of the real prompt/manifest files once those exist (Days 3/4/6) — until then they're explicit placeholder strings, not silently-wrong hashes. Verified per Block 7's done-when: `scripts/verify_wandb.py` ran `start_run` → logged a real two-row `generations` table via `log_table()` → the run appeared at `wandb.ai/joshi0494/legalpsy/runs/ii8ms30i` named `eval-qwen3.5-4b-cuaddev-v1-260819-7892478` (exact scheme match) → deleted via the API in the same script, so the smoke test is repeatable and never leaves clutter behind.
Revisit if: a public release makes the personal `joshi0494` entity worth migrating to a team entity; multiple corpora (MAUD, ContractNLI) make the undelimited `split` token (`cuaddev`) ambiguous and it needs an explicit separator; the `predict`/`score` split (`PLAN-DAYS-1-7.md` Day 6 — re-score without re-generating after a metrics bug) turns out to need its own decision on whether a re-score opens a new W&B run or updates the existing one in place; or real (non-`abl`/debug) runs need an enforced clean-git-tree check before `git_sha` is trusted.
